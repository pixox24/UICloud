# 源文件自动提取预览图设计

## 背景

当前项目已经支持：

- 普通图片上传后自动生成多尺寸缩略图
- 颜色提取、比例识别、方向识别
- 批量上传与同步返回结果

但对于设计源文件，尤其是 `psd` 和 `ai`，仍然需要额外上传缩略图。这个流程对管理员不友好，也容易造成漏传。目标是在保留现有项目结构的前提下，让常用源文件在上传后自动生成预览图，并继续接入现有缩略图和筛选体系。

## 目标

- 上传 `psd`、`ai`、`eps`、`pdf` 时，服务端自动提取一张预览图
- 预览图生成成功后，继续生成 `large`、`medium`、`small` 三套缩略图
- 上传接口保持“单文件同步完成后再返回结果”
- 批量上传时支持多个文件并发，但服务端转换并发做上限控制
- 自动提取失败时不阻断上传，使用默认占位图兜底

## 非目标

- 本阶段不处理 `fig`、`sketch`、`xd` 的自动预览提取
- 不引入独立任务队列、消息队列或后台 Worker 系统
- 不依赖 Photoshop、Illustrator 等 Adobe 桌面软件
- 不把预览生成改为异步补偿模式

## 推荐方案

采用“本机工具链 + 同步上传处理”方案：

- 在当前 Windows 共享机上安装 `ImageMagick`
- 安装 `Ghostscript` 作为 `ai`、`eps`、`pdf` 等格式的渲染依赖
- Next.js 在上传源文件后直接调用外部命令生成预览图
- 预览图输出到 `uploads/thumbnails/original/`
- 再复用现有 `generateThumbnails()`、颜色提取和视觉元数据分析链路

选择该方案的原因：

- 最适合当前“本地一台长期在线的共享电脑”部署方式
- 不依赖 Adobe 软件和 COM/脚本环境，部署更稳
- 可以最大限度复用现有上传、缩略图、筛选逻辑
- 用户体验直接，上传完成时即可看到最终卡片

## 支持范围

第一阶段支持以下格式：

- `psd`
- `ai`
- `eps`
- `pdf`

处理策略：

- `image`：继续走当前 `sharp` 直接缩略图流程
- `psd/ai/eps/pdf`：先提取预览图，再生成三套缩略图
- 其他源文件：保留上传能力，但不强制自动预览，前端显示默认占位图

## 上传处理流程

单文件上传流程如下：

1. 接收上传文件并保存到 `uploads/assets/`
2. 计算文件哈希，执行重复文件检测
3. 判断文件类型
4. 若为普通图片，沿用当前缩略图流程
5. 若为 `psd/ai/eps/pdf`，调用新的源文件预览提取函数
6. 若提取成功，把预览图写入 `uploads/thumbnails/original/`
7. 对原始预览图生成 `large/medium/small` 三套 `.webp` 缩略图
8. 从预览图分析主色、宽高、方向、比例
9. 写入数据库并返回最终结果

批量上传仍维持“每个文件独立请求、每个请求同步返回”的模式。

## 失败兜底

若源文件预览提取失败：

- 上传接口不报整体失败
- 资产记录仍然写入数据库
- `thumbnail_original`、`thumbnail_large`、`thumbnail_medium`、`thumbnail_small` 可为空
- 返回结果中增加明确标记，例如 `previewGenerated: false`
- 前端使用文件类型默认占位卡片展示
- 后续可保留手动补传缩略图入口，但不作为本次实现阻塞项

这样可以避免个别异常文件导致上传流程整体不可用。

## 并发与性能策略

当前设备配置较高（`i7-10700KF`、`64GB RAM`），但站点仍然需要同时承担：

- Next.js Web 服务
- SQLite 读写
- 局域网多用户访问
- 源文件预览转换

因此默认策略为：

- 上传请求保持同步处理
- 服务端源文件预览转换全局并发上限：`3`
- 前端批量上传建议并发：`3`
- 单次源文件预览提取超时：`20s`

这样可以在稳定性和速度之间取得平衡。后续若一段时间内运行稳定，可把全局并发上限调到 `4`，但默认不建议直接使用 `5`。

## 工具链检测

应用启动或首次调用转换前，需要检查：

- `magick -version`
- `gswin64c -version`

若缺失：

- 在启动脚本中提示未安装
- 在上传接口中返回清晰错误或降级到占位图策略

不应出现静默失败。

## 代码层设计

建议新增一个独立工具模块，例如：

- `src/lib/source-preview.ts`

建议包含以下职责：

- `supportsSourcePreview(extension)`：判断是否属于可自动预览的源文件类型
- `extractPreviewFromSource(inputPath, extension, outputBaseName)`：统一入口
- `extractPsdPreview(...)`
- `extractAiPreview(...)`
- `extractPdfPreview(...)`
- `extractEpsPreview(...)`
- `runCommandWithTimeout(...)`

输出统一为一张标准图片文件，推荐先输出为 `.png`，再交给现有 `generateThumbnails()` 统一产出 `.webp` 缩略图。

## ImageMagick / Ghostscript 调用策略

建议使用 `child_process.spawn` 或 `execFile` 调用，避免 `exec` 的命令行长度和转义风险。

约束如下：

- 为每次转换设置超时
- 捕获标准输出和错误输出，便于定位失败原因
- 只对已落盘的本地文件执行转换
- 输出文件名使用系统生成的唯一 ID，避免冲突
- 输出路径固定到 `uploads/thumbnails/original/`

## 数据库与返回结构

本次设计不要求新增数据库字段，因为项目已具备：

- `thumbnail_original`
- `thumbnail_large`
- `thumbnail_medium`
- `thumbnail_small`

但建议上传接口返回中增加更明确的状态字段，例如：

- `previewGenerated: boolean`
- `previewSource: "image" | "source" | "none"`

用于前端更准确展示批量上传结果。

## 前端展示建议

批量上传结果卡片中建议增加：

- “已生成预览” / “未生成预览” 状态标签
- 对源文件显示文件类型角标，如 `PSD`、`AI`
- 预览失败时显示占位图而不是空白区域

这样管理员可以第一时间识别哪些文件需要后续补图。

## 错误处理

需要覆盖以下失败场景：

- 本机未安装 `ImageMagick`
- 本机未安装 `Ghostscript`
- 文件格式异常或内容损坏
- 超大文件转换超时
- 外部命令返回非零退出码
- 输出预览图未成功生成

处理原则：

- 不影响源文件保存
- 不影响数据库主记录写入
- 记录日志，便于管理员排查
- 对前端返回结构化失败信息，但不要让整个批量上传中断

## 测试范围

实现后至少验证以下场景：

- 上传普通 `png/jpg`，缩略图逻辑不回归
- 上传 `psd`，自动生成预览图和三套缩略图
- 上传 `ai`，自动生成预览图和三套缩略图
- 上传 `pdf`，自动生成预览图和三套缩略图
- 上传异常或损坏源文件，上传成功但回退为占位图
- 批量上传 3 个源文件时，接口按预期同步返回
- 并发场景下，站点仍可正常浏览和下载

## 实施顺序

1. 新增源文件预览提取工具模块
2. 在上传接口中接入 `psd/ai/eps/pdf` 预览提取逻辑
3. 增加并发上限和超时控制
4. 调整上传返回结构
5. 优化批量上传结果卡片文案与状态显示
6. 更新 README，写明本机依赖安装方式和失败兜底行为

## 决策结论

本次采用以下正式方案：

- 使用 `ImageMagick + Ghostscript` 作为本机源文件预览提取工具链
- 支持 `psd`、`ai`、`eps`、`pdf`
- 每个文件上传后同步等待预览图与缩略图生成完成再返回结果
- 服务端全局预览转换并发上限默认设为 `3`
- 自动预览失败时不阻断上传，前端回退为文件类型占位图

这套方案最符合当前项目的部署方式、机器条件和维护成本要求。
