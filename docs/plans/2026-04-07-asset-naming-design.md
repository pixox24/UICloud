# 资产自动命名规则设计

## 背景

当前资源库以内部共享为主，资源类型多数为 UI 设计资产。团队希望上传后自动生成统一名称，满足两个目标：

- 名称看起来像内部资产编号，短、规整、便于口头沟通
- 从名称上能大致看出该资源属于什么用途、什么形态

同时，团队还希望编号能反映资源库累计数量，例如看到 `554` 就能大致知道当前库里已有五百多个资源。

## 目标

- 为上传后的资产提供统一的默认命名规则
- 默认命名中必须包含真实资源 ID
- 名称长度尽量短，适合内部协作
- 命名规则能体现“用途”和“形态”
- 用户仍然可以手动修改名称，不做强制锁死

## 非目标

- 不把所有筛选维度都塞进文件名
- 不做复杂的自然语言命名
- 不把后台分类表直接映射为命名码表
- 不追求外部客户可读性，优先服务内部共享效率

## 最终命名格式

采用以下统一格式：

`资源ID_类别码_形态码`

例如：

- `554_UI_H`
- `555_ELM_R`
- `556_MOD_RC`
- `557_NUM_SQ`
- `558_BRD_V`

## 规则解释

### 1. 资源 ID

- 使用数据库中的真实资产 ID
- 不使用前端临时编号
- 不使用时间戳或随机串代替

原因：

- 真正能体现“这是第几个上传的资源”
- 便于团队沟通，例如“看 554 那个资源”
- 自增 ID 最稳定，不依赖前端状态

### 2. 类别码

类别码采用固定用途缩写，第一版仅保留 5 个核心值：

- `UI` = 完整界面
- `ELM` = 元素
- `MOD` = 模块
- `NUM` = 数字
- `BRD` = 品牌

设计原则：

- 类别码表示“资源用途”，不表示文件格式
- 不直接等同于后台分类表
- 第一版先收敛到 5 个核心码，避免上传端过度复杂

## 3. 形态码

第一版仅保留以下形态码：

- `R` = 圆形
- `SQ` = 正方
- `RC` = 圆角矩形
- `H` = 横版
- `V` = 竖版
- `C` = 自定义

补充规则：

- 长横条、Banner、导航等统一归入 `H`
- 不额外拆出“超长横条”独立形态码
- 当系统无法稳定判断时，统一回退到 `C`

## 命名生成方式

采用“半自动”方式：

- 系统自动生成默认名称
- 用户可以手动修改
- 如果用户不改，就使用系统默认名
- 如果用户手动输入名称，就以用户输入为准

这是当前最平衡的方案，因为：

- 自动化程度高，适合批量上传
- 又保留人工修正空间
- 不会强迫所有资源都只能使用机器命名

## 服务端生成策略

由于命名中要求使用真实 `资源ID`，因此默认名称必须在服务端生成。

推荐处理流程：

1. 接收上传请求
2. 保存文件并完成元数据分析
3. 插入资产记录，拿到真实 `id`
4. 根据 `id + 类别码 + 形态码` 计算默认名称
5. 如果用户未手填名称，则回写默认名称
6. 如果用户手填了名称，则保留用户输入

结论：

- 默认名称不能完全依赖前端预生成
- 最终命名应以服务端结果为准

## 形态码自动判断建议

第一版自动判断逻辑建议如下：

1. 如果已知资源应视为圆形，则使用 `R`
2. 如果宽高近似相等，且非圆形，则使用 `SQ`
3. 如果能明确识别为圆角矩形，则使用 `RC`
4. 如果宽大于高，则使用 `H`
5. 如果高大于宽，则使用 `V`
6. 无法可靠判断时使用 `C`

说明：

- `RC` 是否可自动准确识别，需要根据当前缩略图分析能力评估
- 如果第一版无法稳定判断圆角矩形，可先把 `RC` 作为用户可选值或后续补充逻辑
- 形态码本质是“命名辅助维度”，不能影响筛选系统的完整性

## 与筛选系统的关系

命名规则只承担“短识别”职责。

更详细的检索能力仍应由数据库字段承担，例如：

- `file_type`
- `aspect_ratio`
- `orientation`
- `use_scenario`
- `category`
- `tags`

设计原则：

- 文件名保持短
- 结构化筛选交给数据库
- 不把所有信息堆进命名中

## 前端交互建议

上传页建议增加以下交互：

- 新增“类别码”选择项
- 名称输入框旁展示“系统建议名称”
- 当名称输入框为空时，提交后自动使用默认名称
- 当名称输入框有值时，系统不覆盖

如果后续希望进一步增强体验，可增加：

- 形态码预览显示
- “恢复系统建议名”按钮
- 批量上传结果中展示最终命名结果

## 决策结论

本次正式确认如下：

- 自动命名格式为 `资源ID_类别码_形态码`
- 类别码固定为 `UI / ELM / MOD / NUM / BRD`
- 形态码固定为 `R / SQ / RC / H / V / C`
- 长横版统一归入 `H`
- 命名采用“系统默认生成，用户可手改”的半自动方式
- 默认名称必须基于数据库真实资产 ID，由服务端生成

这套规则满足内部资产编号化、简洁化和一定程度可读性的平衡，适合作为当前资源库第一版正式命名规范。
